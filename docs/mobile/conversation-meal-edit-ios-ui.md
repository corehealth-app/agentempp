# Dormant Flow meal editing UI

`FlowConversationModel.open` accepts optional `editing` dependencies. The default is `nil`: this increment installs no route, root factory, release flag, demo success, legacy writer or new backend protocol. The concrete encrypted edit controller and authenticated repositories remain the only Save/Undo path.

The model opens the editor with the original authenticated lifecycle lease. It accepts only the command controller's actual revocable `ConversationCommandContext`; Auth subject, patient owner and backend epoch stay distinct. Suspension hides the form and pending plaintext. A new patient/epoch clears the working form; logout synchronously revokes the lifetime and closes owned work. Ciphertext remains bound to its original account/context. The editor does not manufacture a session, observation or clinical authority.

Each actual current item has a pencil only when the optional dependency exists and the server allows Save. Selecting it performs a fresh owned group GET. Save then calls the concrete controller's fresh eligibility/CAS check and prepares one immutable operation. Name/quantity setters lock before that first await. Save directly applies that operation; it asks for neither meal reconfirmation nor manual calories. `ConversationMealItemEditDraft` preserves the original authored reference: milk mL, whey scoop, decimal comma, explicit grams and renamed-food conversion follow the existing qualified helper. No local macros or new portion rules are calculated.

Persistence failure retains the original prepared UUID, body, CAS and source. Dispatch uncertainty retains the encrypted operation. Closing/reopening the sheet does not make another edit. A cold restart restores the same operation; unknown work blocks a new editor and offers read-only reconciliation. Only an actual matching `absent` response permits an explicit same-body resubmission. Repeating the same current grant preserves that permission; a new grant requires another read. HTTP success alone never closes the operation. A queued snapshot from before an in-flight cancellation cannot authorize discard or another Save. Discard is explicit, exact-ID and restricted to proven unsent work; a later edit requires fresh preparation and a new operation.

Undo buttons follow the actual group's server actions. The confirmation retains the selected group/last operation/CAS. The controller rechecks them against a fresh owned read; the device clock grants no five-minute, day or version eligibility. Failed Undo preparation remains an Undo form, never an empty editable food form.

A typed factual ACK invalidates cached and in-flight current-group reads and records the highest known edit before incrementing the existing official Food/Today refresh signal. A cold-restored ACK still triggers this refresh when the original journal is unavailable; a known conflicting original input hash is refused. A later refresh failure cannot erase success or restore old current numbers. Original receipts and six historical sections stay immutable. All six original sections remain the primary response only while the existing full unchanged-lineage policy proves them current; edited/unavailable lineage shows separate current facts and collapsed original history. No new education, targets or clinical masking is synthesized here.

Journal reads never ACK or delete encrypted work. A bound journal result may resolve only the editor's retained RAM intent after an actual scoped outbox snapshot proves that exact encrypted entry is already absent (for example, deletion completed but visible delivery was cancelled). If the encrypted entry remains, the journal cannot resolve it: explicit controller reconciliation is still required.
