# Native encrypted conversation outbox foundation

This candidate core is not composed into `FlowChatModel`, a repository, a route,
or a release capability. The existing Flow sender is a different protocol and
must not consume these tickets. The four-tab preview remains Debug/demo only.

## Immutable command

`ConversationMealCommand` implements the closed `conversation.command.v1`
`meal.report` body in [command preparation](conversation-command-preparation.md).
Text has a 2,000 UTF-16-unit limit; an optional media caption has a 1,000-unit
limit. Media requires an asset UUID and the explicit consumed-meal action.
Missing optionals are omitted; null and unknown fields are rejected. The client
does not supply owner, nutrition, URL, transcription, epoch or policy authority.

Every new enqueue generates a new UUID, including identical source text. The
canonical wire bytes, SHA-256 input hash and `cmsg1:<lowercase UUID>` identity
remain unchanged across process restart and reconciliation. The saved source
is not trimmed or Unicode-normalized. Native golden hashes are generated by
the actual TypeScript `bindConversationCommand` in base `f10efb91`.

## Account and storage boundary

`ConversationOutboxSession.open` obtains its owner from
`SessionLifecycleProviding.leaseForRequest()`. Callers cannot supply a user ID
to this factory. Local file reads, mutations and visible snapshot publication
use the lifecycle's synchronous patient-state/visible-state gates. Immutable
tickets also bind the owning session instance and local lease generation.
Local generation is not a server epoch.

`EncryptedConversationOutboxStore.device` uses the application's private
Application Support directory, under `performe-conversation-outbox-v1`.
Account filenames and Keychain account names contain a domain-separated
SHA-256 of the authenticated account UUID. No raw account ID, bearer or source
text is written into a filename, lock file or log.

Each account has a random 256-bit AES-GCM key in the existing Keychain API:
service `app.performe.conversation-outbox.v1`, unlocked/this-device-only,
non-synchronizing, no access group. Key creation is add-only; concurrent
creators re-read the winning item. An existing ciphertext file with a missing
or malformed key fails closed, without generating a replacement key.

AES-GCM authenticates format/version and account hash as additional data. The
encrypted envelope also validates version, owner, unique command IDs, frozen
wire bytes/hash and state consistency. A corrupt, foreign or unreadable file
is preserved and reported as an error, never interpreted as an empty queue.

The directory has mode 0700 and is excluded from backup. Ciphertext and lock
files created by the store have mode 0600. On iOS the directory and ciphertext
use complete file protection. The store serializes a full read/mutate/write
transaction and directory protection/backup metadata with an empty store file
lock shared across accounts/processes, writes only ciphertext to a private
temporary file, synchronizes it, then atomically renames it. A failed write
before rename leaves the prior queue unchanged. Tests cover process restart;
this is not a claim of hardware-level power-loss guarantees or memory erasure.

## State machine and recovery

| Operation | Required state | Persisted result |
| --- | --- | --- |
| New enqueue | Valid new source | `queued`, new UUID |
| Prepare dispatch ticket | `queued` | `dispatched-unknown` before ticket return |
| Report uncertain/cancelled/stale/reset result | Original ticket, unresolved command | `waiting-reconciliation` with hold reason |
| Obtain reconciliation ticket | Dispatched or waiting | Same ID, hash and original wire body |
| Discard unsent | `queued` only | Remove only that never-dispatched command |

Unknown outcomes cannot be discarded, blindly dispatched again or renewed as
fresh work. A weaker callback cannot clear a stale-epoch/reset hold. Merely
opening the store creates no registration, reward, duplicate command or
semantic success. Logout/account change invalidates the session's RAM key and
bearer handles and blocks old callbacks/publications while retaining the
account-bound ciphertext and Keychain item. A later authenticated session of
the same account can reconcile the original command.

The pending bound is 50 entries, matching the existing Flow history and
accepted-message cache horizon. Entries and sealed-file bytes are bounded;
there is no silent eviction. `queueFull` requires reviewing pending work;
`storageUnavailable`/`keyUnavailable` require retrying access while preserving
the queue; `integrityFailure` requires recovery without overwriting the file;
`reconciliationRequired` keeps the original command pending. These are typed
core errors; no new technical settings or placeholder success UI are exposed.

## Integration gates

There is intentionally no acknowledgement API or HTTP-200 success shortcut.
The final typed server receipt must bind authenticated account, exact command
ID, input hash, server epoch, session ownership and a terminal journal/effect
snapshot before an acknowledgement/removal transition can be introduced.

Before activation, the new transport/reconciliation adapter must validate its
current session immediately before network work, preserve unknown outcomes,
handle typed reset/stale-epoch refusal, and publish through the visible-owner
gate. Composition must own and invalidate the outbox session on logout and
screen/session disposal. Explicit account deletion or local reset needs a
separate authorized retention policy; this core does not delete such files.
The current RAM-only legacy Flow outbox is unchanged until that integration
is qualified. No workout command, server epoch or receipt contract is invented
here, and no server route or capability is enabled by this increment.
