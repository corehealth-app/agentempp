# Native historical feedback presentation reader

The dormant native `ConversationFeedbackPresentationSnapshot` decodes the actual
`conversation.feedback-presentation.v1` output at root commit
`794850c361bf0499fec660d034458c5a8d8fd14d`. It is separate from the immutable
registration v1/v2 receipt readers and their existing history admission rules.
No repository, route, feature flag, transport or outbox acknowledgement is enabled.

## Contract and rendering

The decoder checks closed root/nested objects, historical mode, Flow AI identity,
meal registration identity, civil dates, UUIDs, current policy and exact provenance
observation. It accepts only the three actual variants:

- Available `sections`: original v2 identity, closed saved meal facts and exactly
  six ordered server sections: saved/items/summary/day/block/education.
- Available `legacy`: original v1 identity and a closed existing v1 body, only when
  assessment is complete, recording is allowed, pause is false and every hide
  flag is false. The body must bind the same meal registration and historical day.
- Unavailable `placeholder`: restricted original v1, exactly saved/summary sections,
  without opaque legacy text or raw recorded facts.

The actual core public-policy projection includes `hide.budget` alongside the five
flags declared by the older native/TS interface. This wrapper retains all six in
its own Policy, requires all six and treats any true flag as restricted. Existing
read-surface policy compatibility is unchanged. Unknown additions fail closed.

`ConversationFeedbackPresentationView(feedback: Bound)` displays server section
text with SwiftUI `Text(verbatim:)`. It does not invoke the original v2 renderer,
regenerate numbers, infer missing targets, convert units, select education or
re-mask prose. Saved mass, declared display quantity, nutrition source, per-item
facts and independent saved totals remain distinct. Historical day/block texts
come from the current-policy server projection; this is never a Today panel or a
rewritten immutable receipt. The header identifies Flow AI and the historical date.
Malformed/unknown optional enrichment must be discarded by the future parent
response DTO without invalidating a factual registration.

## Session and identity boundary

The payload has no owner ID or authentication signature. A successful decode is
not proof of ownership, a saved meal or an outbox ACK. After trusted authenticated
transport, the future adapter must construct `Scope(ownerID:sessionGeneration:epoch:)`
from the original session lease and actual server journal binding, and `Binding`
from that command's factual receipt: command/registration/date/meal kind/log IDs
and admitted timestamp. It must pass a freshly validated current Scope to
`bound(to:current:)`. Raw owner, generation, epoch, command and registration
identities must agree; saved item log IDs are compared as a unique exact set.
RFC3339 fences preserve nine fractional digits and reject a pre-admission observation.
V1/placeholder have no item IDs, so those log facts remain the adapter's factual
receipt responsibility and cannot be proved from opaque text.

Only `Bound` is accepted by the component. The future adapter must publish through
the existing `performVisiblePatientStateOperation(lease:operation:)` session gate,
clear bound presentation on account/generation/reset changes, and obtain a new
current-policy presentation when revisiting. This value is an observation, not a
permanent clinical grant. This leaf contains no asynchronous callback or session
provider and cannot validate a lease by itself.

## Evidence and gates

Fixtures are generated by the actual TS presentation service with its real
clinical projection and original-feedback fixtures, using injected local sources
only. Native tests preserve all six fixtures verbatim and cover restricted legacy,
closed variants, malformed/private fields, original facts, account/session/epoch
binding and sub-millisecond fences. Tests include the existing immutable v1/v2
neighbors. The project uses filesystem-synchronized source groups, so new Swift
files need no persistent project entries. Focused native QA may temporarily limit
test compilation membership; the pbxproj must be restored byte-identically.

Route/response envelope integration, current-session lifecycle publication,
terminal receipt validation/outbox ACK and real authenticated SDK-to-native QA
remain separate activation gates. No provider/PG/cloud/physical-device operation
is performed by this increment.
