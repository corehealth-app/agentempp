# Training execution — T5 implementation in progress

The approved conversational plan remains the delivery contract. The source contains a preparation kernel, private SQL persistence, original-Auth server adapter and three additive HTTP routes. The handlers, real service and kernel have been qualified against disposable local PostgreSQL and, subsequently, real Supabase Auth/API in a dedicated staging QA preview. **The native execution UI and client release are still pending.** Persisted per-exercise execution is not yet delivered to clients.

`training-execution-kernel.ts` projects the server-owned current training plan and prepares start/update transitions. The selected plan UUID/version/content hash and exercise ordinals are pinned in the session. Two exercises with the same name retain different identities. Recommendations remain separate from actual set UUIDs, repetitions, kilograms, duration and completion; missing actual values remain null, and zero stays zero.

Closed commands support starting, saving/removing a set, marking an exercise and abandoning the session. They reject client owner, clinical, calorie or XP overrides. Marking an exercise does not seed prescribed sets, write a workout, credit a block or change the food budget. A completed registration remains a separate future integration with the existing protected workout service, exactly once per execution session.

Updates require original owner/Auth, epoch, timezone, open session day and revision. The session day is checked against the actual start instant in the pinned timezone; progress may cross midnight while that original day stays open. A receipt must belong to this session and its chronology. Replaying an accepted operation returns its immutable receipt alongside current state, including after abandonment/day closure; it never restores an old state.

The SQL store locks the original owner/workouts lane and epoch, recaptures the pinned session day under the existing day lock and compares the complete capture token before storing state, a unique operation receipt and the minimal audit delta in one transaction. Updates independently restrict the state change to the closed command. The kernel remains the semantic validator and projector of the captured official plan; a prepared payload is never accepted from an HTTP client. The authenticated-transport migration supersedes the initial preparation's epoch initialization: **reads require an existing official epoch and never create an epoch, session or receipt**. The five-minute freshness limit applies to new writes, while an accepted operation can replay later using its immutable receipt and current state. Replay still fences original Auth, epoch and timezone, including a change between preparation and commit.

Three private RLS tables have no direct grants to end-user or service roles. Only the two backend RPCs grant execute to `service_role`; both also use the trusted-backend guard and the current user/Auth binding. Reset scrubs execution state, receipts and audits in the existing epoch lane; account deletion cascades the same owned data. RPC errors and lost replies do not trigger an automatic write retry. A caller retries the original operation UUID, never a newly generated ID for an uncertain request.

The HTTP runtime uses only the three `*_authenticated` RPCs. It first verifies the bearer through the existing Supabase `getUser` authentication and existing-account observer, then extracts the original `session_id` from that verified token. It never uses token metadata for ownership or role decisions. SQL checks the same live `auth.sessions` row, owner, original Auth and non-admin identity under a short `FOR SHARE NOWAIT` lock. An in-flight logout/session change returns a conflict instead of waiting; natural expiry during the writer rolls back the entire state/receipt/audit transaction. The runtime repeats original authentication and entitlement checks before RPCs and before publishing the response. No refresh token or JWT is stored in the execution tables.

## HTTP contract (default disabled)

All three routes require the normal bearer and `X-Training-Owner`. They are unavailable unless `MOBILE_TRAINING_EXECUTION_ENABLED=true`. This flag is enabled only in the new dedicated QA preview; existing distributed native origins and the registered media worker were preserved.

| Route | Contract |
| --- | --- |
| `GET /api/mobile/v1/training/execution` | `training.execution-home.v1`: official scope, current plan, up to 20 resumable summaries and a closed cursor. |
| `GET /api/mobile/v1/training/execution/:sessionId` | `training.execution-read.v1`: scoped durable execution, not a reconstruction from the prescription. |
| `POST /api/mobile/v1/training/execution/commands` | Closed kernel command; also requires `X-Training-Epoch` and `Idempotency-Key: texecution1:<operation_id>`. |

Home accepts only the optional JSON `cursor` query. It binds owner, epoch, timezone and the last timestamp/UUID; other queries are rejected. Resumption includes only current-epoch, original-Auth, matching-zone sessions in progress whose original day remains open. Abandoned sessions and closed days remain readable as history but are not offered for resumption. Commands accept no client-provided prepared state, owner, calories or rewards. After an uncertain response, retain the original operation ID and reconcile/retry that operation; a second intentional execution uses a different ID.

`training-execution-store.ts` binds owner and original Auth when constructed, validates the closed command before capture, uses the real preparation kernel and checks persisted receipts/state. A fresh reply must equal the prepared result. Replay returns the original receipt alongside current state, without a new audit. Reopening through the adapter reads the durable state rather than reconstructing prescribed sets.
