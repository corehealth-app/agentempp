# Native linked meal replies (dormant candidate)

The existing bundled `meal_command_v1` runtime installs the real typed reply controller explicitly; its release default remains off. The ordinary `FlowConversationModel.open` default does not install it. The report protocol remains `conversation.command.v1` and the explicit history reader remains v2. This increment does not enable a server flag, release configuration or route, and does not implement the separate child current-group/edit protocol.

A question is accepted from the owned v2 thread or a successfully delivered typed result. Its parent binding, decision hash, question key/revision, original answer, reply UUID and exact submission bytes are frozen. Quantity answers carry the original amount/unit (including mL/caneca/scoop when the real question permits them); the app does not convert them into grams or invent a meal type, food name, nutrition, source, server clock or consumption claim. The backend CAS admits the current question. The original negative report stays separate from its genuine continuation child.

Reports and replies share the existing Auth-subject encryption key, file/directory namespace, private atomic transaction/lock and total fifty-intent/byte budget. Format v1/v2/v3 files are read without rewrite or inferred patient/epoch. Report-only writes retain v3 until the first typed reply transaction. A v4 transaction contains both collections, preserves exact original report/reply bytes and never downgrades, including when its last reply closes. Legacy missing bindings remain held. The already-qualified separate edit queue keeps its existing limit; no third queue, key or file is introduced.

Every send persists dispatched-unknown before the one physical POST. Its key is `cmreply1:<original reply UUID>`; its hash covers the nested original clarification input using the existing qualified canonicalizer. The protected owner and epoch headers are preconditions, not write authority. An HTTP 401 cannot refresh and replay a reply POST. Timeout, cancellation, 202, malformed/foreign responses, conflict and network loss preserve unknown ciphertext. A restart restores the same intent and uses GET with the exact original parent/reply hashes. Journal history, a current head or HTTP 200 alone never closes the queue.

Root's technical delivery rule permits removal after an exact POST/reply-GET result with genuine own child binding and current Auth/patient/epoch/lifetime: either the actual saved continuation effect/fulfillment, or HTTP 200 needs_reply with the exact original expected revision plus one and a new question key. The latter is non-food answer delivery, not a food acknowledgement, registration, reward or macro change. Higher/stale question revisions remain unknown. Saved optional feedback can be null without losing the factual effect. Its historical public wrapper is rebound to the actual child and passed to the existing masked six-section renderer; it is never relabeled v1 or current meal facts.

A GET 200 held can permit one separate user action to resume the SAME original POST only for ready_for_explicit_resume or awaiting_explicit_resume with genuine own child/parent/decision/hash/epoch under the exact current grant. GET never sends automatically. Superseded, fulfilled, source/question/day conflicts, missing child and permanent reset/stale/server-changed holds cannot grant this permission. Permissions are consumed before transport and revoked by refresh/account/epoch changes. SQL rechecks source/day and remains the final fence.

The actual form locks its question, meal selection, quantity/unit and immutable intent after preparation, including local persistence uncertainty. It exposes explicit status check, one-use resume, and discard only while proven never dispatched. Logout/remap synchronously redacts public getters and asynchronously cancels only owned work/clears RAM; ciphertext remains bound to its original Auth account and patient/epoch. Atomic factual deletion can precede a later account change; the subsequent visible gate suppresses publication and never recreates work.

Verification is scoped in the external task evidence. URLProtocol/Foundation/native component tests are not authenticated BFF-to-native E2E, provider QA, cloud deployment or activation. Public reply HTTP qualification and child-group v2 actions remain separate gates.
