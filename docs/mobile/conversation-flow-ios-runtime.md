# Real Flow app composition, default off

The command Flow now has an actual app composition path, not only an injected preview component. `AppDependencies.flowConversationSessions` is an inert concrete factory. `Prompt14SessionOwner` owns its coordinator; the selected Flow root opens it asynchronously, and owner withdrawal synchronously hides the old model and starts joined asynchronous teardown. Loading/unavailable/retry are real factory states. Once this path is selected, a failed session/protocol read never falls back to the legacy agent writer or a demo transcript.

`PERFORME_FLOW_COMMAND_RUNTIME` is a bundled build selection. Absence or `legacy` keeps the existing release shell. `meal_command_v1` may install the source only with real Supabase authentication, a lifecycle-bound `MobileAPITransport`, the complete current-clinical family and an existing `CurrentClinicalQABinding.candidate` matching the exact API/Storage origins. The stable old endpoint with an absent QA binding cannot select this source. Unknown selections install no command capability. No Info.plist value, deployment, server flag or endpoint setting is changed by this increment.

The code path is compiled for Release/TestFlight and Debug. An explicitly configured Debug real candidate uses the existing real-account launch configuration; explicit test/demo fixtures retain precedence. Launch arguments can opt out into an isolated test/demo but cannot grant the command runtime, authentication, a patient, epoch or clinical policy. A future approved compatible candidate build can select the same factory without rewriting it. QA metadata is provenance selected by the build producer, not authenticated clinical or account authority; actual authenticated protocol/session and current-clinical readers remain mandatory.

The source captures the current Auth lease and compares it to the original authenticated shell owner before doing work. Optional `expectedLease` is threaded through `FlowConversationModel.open` and both command/edit controller factories, preventing a later open from recapturing a replacement account. Repositories, outboxes, media, history and editing retain this lease; patient owner and epoch are discovered by the actual closed command-session GET. Bound publication crosses the original lifecycle's visible-state gate and the model's current revocable command authority. No server observation is constructed by the factory or shell.

Production defaults use the existing protected Keychain services and private encrypted report/edit stores, with their original account namespaces, patient/epoch provenance and immutable UUID/body/hash rules. There is no RAM-only outbox substitute, automatic replay, fabricated ACK or nutrition write in composition. Withdrawal schedules cleanup immediately, independently of other shell readers draining; explicit owner teardown joins that same task. Local ciphertext remains available to its original account and context. This local lifecycle fence makes no new claim about remote token revocation or hardware power-loss durability.

Media composition supplies the existing `StorageUploadTransport` for the already matched Supabase origin and one shared protected `MediaStagingStore`. The actual Flow capture view uses `MealMediaStager`, device camera/gallery and the existing audio recorder. Construction requests no media permission and uploads nothing. Capture/processing/asset attachment still use the actual model context and owned media service; no signed media URL enters a command body or outbox.

The four visible tabs reuse the existing stable raw route identities: Flow, Alimentação, Treino and Jornada. Both build flavors can select this presentation only from a composed real source (the old isolated demo preview remains separate). Profile, Library, Today/routine, re-evaluation, structured registration, all plans and old conversation/history destinations remain secondary routes. Legacy conversations stay readable; their sender is disabled within the new shell. Official Food/Today refresh follows the actual owned Flow ACK signal. Alimentação/Treino currently reuse official plan readers, and Jornada reuses the actual Progress feature. Planned day/week consumed comparisons, richer training execution and social scope are not represented as completed by this navigation work.

Activation remains a separate gate: the deployed old backend has not acquired this capability merely because the source compiles. A compatible verified HTTPS candidate, actual authenticated native/backend QA, and an approved bundled target selection are required before enabling it. This increment introduces no loopback/TLS/clinical-binding exception and creates no paid environment. The first known-meal `conversation.command.v1` path can be qualified independently; linked clarification/answer protocol work remains separate. The pre-existing candidate plan-import completion host issue and four-tab guided-tour adaptation remain explicit activation follow-ups; no fake success screen fills these gaps.

Foundation tests exercise real source/controller/outbox/repository code with controlled HTTP and synthetic protected storage, including wrong/superseded Auth, distinct patient binding, mid-open account switch, late owner withdrawal, immediate retirement, retry and ciphertext preservation. Native gates compile the full app and check actual dependency-family selection, both flavor route mapping and focused neighboring behavior. Such results are focused native QA, not full native regression, provider qualification or authenticated native/backend E2E.
