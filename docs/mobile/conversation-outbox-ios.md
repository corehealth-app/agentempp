# Native encrypted conversation outbox foundation

This candidate core is not composed into `FlowChatModel`, a repository, a route,
or a release capability. The existing Flow sender is a different protocol and
must not consume these tickets. The four-tab preview remains Debug/demo only.

## Immutable command

`ConversationMealCommand` implements the closed `conversation.command.v1`
`meal.report` body in [command preparation](conversation-command-preparation.md).
Text has a 2,000 UTF-16-unit limit; an optional media caption has a 1,000-unit
limit. Media requires an asset UUID and the explicit consumed-meal action.
Missing optionals are omitted; null and unknown fields are rejected. The client
does not supply owner, nutrition, URL, transcription, epoch or policy authority.

Every new enqueue generates a new UUID, including identical source text. The
canonical wire bytes, SHA-256 input hash and `cmsg1:<lowercase UUID>` identity
remain unchanged across process restart and reconciliation. The saved source
is not trimmed or Unicode-normalized. Native golden hashes are generated by
the actual TypeScript `bindConversationCommand` in base `f10efb91`.

## Immutable original backend epoch

Every new `enqueue(..., server:)` requires a
`ConversationOutboxServerObservation(ownerID:localSessionGeneration:epoch:)` from
the future trusted authenticated backend capability adapter. The session checks
owner and local generation against its actual captured lease. The observation
is a caller trust boundary, not a signature or a proof that an old callback is
current. Freshness must be fenced by that adapter through the actual session
gate. UUIDs cannot order resets; no queue-wide epoch sweep is performed.

The entry and dispatch/reconciliation ticket retain `originalServerEpoch`.
`prepareDispatch(commandID:server:)` requires the same epoch and no hold, then
persists unknown before returning bytes. A different observation refuses without
writing, so a late E1 observation cannot hold or retag E2 work. The future service
uses this original epoch as an admission precondition, not a command/source input
or clinical authority. Canonical wire bytes/hash and `cmsg1` remain unchanged.

Backend stale/reset responses use the exact dispatched ticket in `markWaiting`.
An explicit local reset uses a separate read-only `decisionTicket` and
`holdForLocalReset`, bound to session instance, owner, generation, exact body/hash
and original epoch. Decision tickets authorize neither transport nor ACK. Holds
are durable and monotonic; observing the old epoch again never clears a hold.
Copied dispatch bytes cannot be revoked by a later local hold: the future
transport must revalidate scope immediately before send, and SQL remains the
last expected-epoch fence.

## Account and storage boundary

`ConversationOutboxSession.open` obtains its owner from
`SessionLifecycleProviding.leaseForRequest()`. Callers cannot supply a user ID
to this factory. Local file reads, mutations and visible snapshot publication
use the lifecycle's synchronous patient-state/visible-state gates. Immutable
tickets also bind the owning session instance and local lease generation.
Local generation is not a server epoch.

`EncryptedConversationOutboxStore.device` uses the application's private
Application Support directory, under `performe-conversation-outbox-v1`.
Account filenames and Keychain account names contain a domain-separated
SHA-256 of the authenticated account UUID. No raw account ID, bearer or source
text is written into a filename, lock file or log.

Each account has a random 256-bit AES-GCM key in the existing Keychain API:
service `app.performe.conversation-outbox.v1`, unlocked/this-device-only,
non-synchronizing, no access group. Key creation is add-only; concurrent
creators re-read the winning item. An existing ciphertext file with a missing
or malformed key fails closed, without generating a replacement key.

AES-GCM authenticates format/version and account hash as additional data. The
encrypted v2 envelope (`PCOBX002`, version2 AAD) also validates version, owner,
unique command IDs, frozen wire bytes/hash/epoch, epoch provenance and state
consistency. Existing retained entries cannot change epoch/body/provenance,
lower a hold or return dispatched work to queued. A corrupt, foreign or unreadable file
is preserved and reported as an error, never interpreted as an empty queue.

The directory has mode 0700 and is excluded from backup. Ciphertext and lock
files created by the store have mode 0600. On iOS the directory and ciphertext
use complete file protection. The store serializes a full read/mutate/write
transaction and directory protection/backup metadata with an empty store file
lock shared across accounts/processes, writes only ciphertext to a private
temporary file, synchronizes it, then atomically renames it. A failed write
before rename leaves the prior queue unchanged. Tests cover process restart;
this is not a claim of hardware-level power-loss guarantees or memory erasure.

The owner hash, directory, filename and Keychain service remain v1 identities so
existing ciphertext is discoverable. A separate closed decoder opens
`PCOBX001` with version1 AAD. Reading v1 does not rewrite it. Missing epoch is
never filled from the current capability: migrated entries retain explicit
`legacy-v1-missing` provenance and nullable epoch. Legacy queued stays queued
with a hold, preserving known-unsent discard; legacy dispatched/unknown stays
undiscardable waiting work. Existing holds remain intact. No dispatch or
reconciliation-send ticket is available without an original epoch. A later
legitimate mutation rewrites the complete queue as v2 under the same file lock
and atomic ciphertext replacement; failed migration preserves exact old bytes.

## State machine and recovery

| Operation | Required state | Persisted result |
| --- | --- | --- |
| New enqueue | Valid new source and trusted session-bound backend epoch | `queued`, new UUID and immutable epoch |
| Prepare dispatch ticket | `queued`, no hold, matching original/current epoch | `dispatched-unknown` before ticket return |
| Report uncertain/cancelled/stale/reset result | Original ticket, unresolved command | `waiting-reconciliation` with hold reason |
| Obtain reconciliation ticket | Dispatched or waiting | Same ID, hash and original wire body |
| Explicit local reset | Exact read-only decision ticket | Permanent reset hold; preserve known-unsent/dispatched distinction |
| Factual terminal ACK | Exact dispatched/reconciliation ticket and actual closed saved packet | Atomically remove only matching command, then visible-owner publication |
| Discard unsent | `queued` only, including held legacy known-unsent | Remove only that never-dispatched command |

Unknown outcomes cannot be discarded, blindly dispatched again or renewed as
fresh work. A weaker callback cannot clear a stale-epoch/reset hold. Merely
opening the store creates no registration, reward, duplicate command or
semantic success. Logout/account change invalidates the session's RAM key and
bearer handles and blocks old callbacks/publications while retaining the
account-bound ciphertext and Keychain item. A later authenticated session of
the same account can reconcile the original command.

The pending bound is 50 entries, matching the existing Flow history and
accepted-message cache horizon. Entries and sealed-file bytes are bounded;
there is no silent eviction. `queueFull` requires reviewing pending work;
`storageUnavailable`/`keyUnavailable` require retrying access while preserving
the queue; `integrityFailure` requires recovery without overwriting the file;
`reconciliationRequired` keeps the original command pending. These are typed
core errors; no new technical settings or placeholder success UI are exposed.

## Integration gates

`SavedConversationMealCommandResultSnapshot` decodes the actual closed
`conversation.meal-command-result.v1` / `saved` packet. It validates canonical
owner/command/hash/epoch, admitted time and the actual closed
`conversation.meal-effect.v1` receipt: owner/command/hash consistency, provider
key, registration/log UUIDs, unique bounded log IDs, meal type, effect-version
format, civil date/timezone and nanosecond consumed>=admitted ordering. It never
recomputes the opaque SQL effect hash or treats schema validation as DB proof.

`acknowledgeSaved(ticket:resultData:server:publish:)` requires trusted authenticated
transport, current actual lease, owning ticket instance/generation, exact frozen
command bytes/hash/ID/Idempotency-Key, original epoch and current trusted
observation. A declared command meal type must match the factual receipt. It
refuses queued, reset/stale-held, foreign, unbound or missing local work. Removal
of that exact command occurs inside the actual patient-state gate and atomic
disk transaction. Publication of typed receipt and bound historical presentation
then occurs inside the visible-session gate. If the account changes after the
valid A deletion, B receives no publication; this does not roll back A's factual
ACK or authorize recreating the command. Duplicate ACK produces no new success.
A failed storage write preserves pending work and publishes nothing.

Feedback is optional: null, malformed, wrong-bound or oversized presentation is
dropped without invalidating the saved factual result. Valid feedback is only
the separate current-policy historical wrapper, with actual command/epoch,
registration/day/meal/log binding and observation fence. Raw immutable v2 is
not accepted as public presentation. The seven native golden packets come from
the actual BFF `projectSavedConversationMealCommandResult`, not fabricated HTTP
success data. A status code alone never acknowledges anything.

Before activation, the new transport/reconciliation adapter must validate its
current session immediately before network work, preserve unknown outcomes,
handle typed reset/stale-epoch refusal, and publish through the visible-owner
gate. Composition must own and invalidate the outbox session on logout and
screen/session disposal. Explicit account deletion or local reset needs a
separate authorized retention policy; this core does not delete such files.
The current RAM-only legacy Flow outbox is unchanged until that integration
is qualified. No workout command or server authority is invented
here, and no transport, server route or capability is enabled by this increment.
