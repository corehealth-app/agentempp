# Conversational workout backend

This increment provides an executable, additive server core. Capability, public/native intake, feedback v3, conversational edit/Undo and a combined meal/activity history remain pending. It is not full Flow or Roberto acceptance and does not activate a new endpoint. The older SQL prototype in `docs/mobile/prototypes/` is historical design evidence; do not apply it in place of the concrete migration.

## Authority and identity

The internal `conversation.command.v1` / `workout.report` body preserves the exact text or exact owned processed media identity. It does not authorize a performed activity. A later shared server intake must route unequivocal performed text without a manual workout selector; old `meal.report` bytes/hash may never be silently retyped. Mixed performed food/activity source is preserved and remains unresolved until an explicit multi-effect integration ruling exists.

The concrete SQL independently rebuilds the complete performed clause from stored text/caption/audio transcript and the locked active catalogue. Questions, future, habit, negation, third-party, mixed or unsupported clauses do not write a workout. Equipment alone is not performed proof. Missing necessary duration keeps one immutable question. The current bounded literal interpreter is not a claim of unrestricted natural-language coverage or conversational question answering.

Owner/UUID/hash/epoch form permanent identity; SQL and TS canonical prepared hashes agree against real PostgreSQL golden fixtures. One UUID replays its original immutable preparation/receipt. Two otherwise identical activities with different UUIDs produce two workouts; there is no time-window dedupe. Meal, meal reply and workout admissions share the existing ten new identities per rolling minute, with free same-identity replay and bidirectional kind fencing.

## Executable core and guard boundaries

`20261104235316_conversation_workout_atomic.sql` adds service-only admission, source, preparation, atomic commit, receipt read and read-only reconciliation. It reuses the established owner/epoch locks, current clinical capture, exact catalogue and strength fact/operation substrate. It never calls the legacy six-hour/UI writer or pretends the provenance is `ui-v1`. Provenance is explicitly `conversation.workout.v1`.

A commit locks the current owner/epoch/command, recaptures and compares clinical/config/catalogue/media/calendar authority, and rejects a closed day. Workout, snapshot aggregation, strength fact/operation, immutable receipt/original facts and journal event commit together. A failed mandatory insert rolls all those effects back. Original receipt/facts survive removal of the live row. Reconciliation reads those facts and current presence; it never re-extracts or re-estimates to repair a lost response.

The backend SDK adapter requires a supplied fresh Auth/admin/current patient mapping/clinical epoch observer. It checks before and after every physical RPC, latches a scope failure across internal catches and dispatches no later RPC. The effect writer keeps its own physical guards; no duplicate outer writer observation is introduced. Rich mutation data is never acknowledgement: only the same-identity durable receipt read can acknowledge success. No public factory silently supplies a permissive observer.

Epoch reset invalidates permanent identities and scrubs source, preparations, effects and events through owned FK cascades. An old UUID remains stale in the new epoch. Tables have RLS and no direct client/service-role access; only the named public RPCs are granted to service_role. The SQL guard still rejects an untrusted claim independently of application typing.

## Energy coverage and compatibility

`workout_logs.estimated_kcal` was already nullable. The migration does not change its nullability or add an energy formula. The existing `calc_workout_kcal` is called only with exact active catalogue, actual captured current weight and explicit intensity. Missing/unsupported inputs or a NULL calculator result stay NULL; there is no 70kg, moderate-intensity or zero substitute.

`daily_snapshots.exercise_calories` and its generated balance remain the existing numeric storage. `exercise_energy_complete=false` marks that stored sum as only a known partial sum. Backfill proves each associated old workout row: preexisting NULL makes coverage false; a proven empty/known set may be true. The I/U/D trigger recomputes the known sum and marker, so unknown→known correction, reversal and removal can restore availability. Every physical change also refreshes the snapshot timestamp even when NULL/zero energy leaves its aggregates unchanged; second activity, duration-only edit and removal must invalidate the scalar reader latch. It does not rewrite progress/XP or recalculate a closed ledger. SQL qualification exercises these row changes directly; a conversational correction/Undo API is still pending.

Today explicitly negotiates `clinical_policy=current_clinical_v1&day_energy=field_availability_v1`. The result is `bodyflow.daily-state.v4`, with nullable `exercise_kcal`, `exercise_energy` and `daily_balance_energy`. Unknown exercise hides only exercise and an exercise-dependent balance. Official food, protein, hydration and previously consolidated block progress remain independent. Existing gain/maintenance balances exclude exercise and remain available when otherwise proved. Current clinical masks still win. Legacy known-complete Today keeps v3 numbers/shape; an unknown day requires an updated representation rather than publishing the partial numeric sum. Native v4 consumption/stale-state clearing is pending, so activation remains blocked.

Coverage participates in snapshot selections and consistency fingerprints; a marker-only change invalidates a read even if the numeric sum/timestamp is unchanged. Legacy trends refuse incomplete numeric exercise; a nullable trends representation remains pending. V1/v2 receipt reads/replays stay immutable. A NEW v2 numeric day seal with an explicit incomplete source marker is refused; additive feedback v3 must retain the independently proved food/protein section before activation. `day:null` is only an interim legacy boundary, not the final experience.

The shared, clinical and Inngest closers withhold new dependent energy credit when coverage is incomplete while retaining the existing XP/status policy. The SQL finalizer independently refuses an open-day block ledger change when marker/actual owned rows show unknown energy. Closed replay returns before recalculating progress. Whole-history recomputation refuses unknown coverage rather than inventing a replacement for consolidated progress. New unknown-energy close results explicitly use `calculation_version: bodyflow.day-close.v2`, `detail.exerciseCalories: null`, `detail.exerciseEnergy: {status: unavailable, reason: unknown_workout_energy}`, and preserved-unknown block status. A closed server parser accepts that shape separately from the unchanged legacy numeric result; NULL without the version, partial0 with v2, contradictory availability or unknown-energy credit are refused. Completed telemetry also has NULL exercise plus an explicit false coverage marker. Current discovery/hook consumers forward closed/progress and do not sum or coerce the nullable energy. Actual PG legacy-before-migration replay and repair tests preserve the old receipt byte-for-byte. This is an availability guard, not a reward-policy change or an immediate activity credit.

This is SQL-body concurrency evidence, not public RPC/HTTP/E2E qualification.
