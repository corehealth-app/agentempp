# Training execution — T5 implementation in progress

The approved conversational plan remains the delivery contract. The source now contains a preparation kernel, private SQL persistence migration and original-Auth server adapter. They have been qualified together against disposable local PostgreSQL, **not installed in staging or exposed as an HTTP/native feature**. Persisted per-exercise execution is not yet delivered to clients.

`training-execution-kernel.ts` projects the server-owned current training plan and prepares start/update transitions. The selected plan UUID/version/content hash and exercise ordinals are pinned in the session. Two exercises with the same name retain different identities. Recommendations remain separate from actual set UUIDs, repetitions, kilograms, duration and completion; missing actual values remain null, and zero stays zero.

Closed commands support starting, saving/removing a set, marking an exercise and abandoning the session. They reject client owner, clinical, calorie or XP overrides. Marking an exercise does not seed prescribed sets, write a workout, credit a block or change the food budget. A completed registration remains a separate future integration with the existing protected workout service, exactly once per execution session.

Updates require original owner/Auth, epoch, timezone, open session day and revision. The session day is checked against the actual start instant in the pinned timezone; progress may cross midnight while that original day stays open. A receipt must belong to this session and its chronology. Replaying an accepted operation returns its immutable receipt alongside current state, including after abandonment/day closure; it never restores an old state.

The SQL store locks the original owner/workouts lane and epoch, recaptures the pinned session day under the existing day lock and compares the complete capture token before storing state, a unique operation receipt and the minimal audit delta in one transaction. Updates independently restrict the state change to the closed command. The kernel remains the semantic validator and projector of the captured official plan; a prepared payload is never accepted from an HTTP client. A first capture initializes the existing shared epoch if absent, under the owner lock; it creates no training log or clinical target. The five-minute freshness limit applies to new writes, while an accepted operation can replay later using its immutable receipt and current state. Replay still fences original Auth, epoch and timezone, including a change between preparation and commit.

Three private RLS tables have no direct grants to end-user or service roles. Only the two backend RPCs grant execute to `service_role`; both also use the trusted-backend guard and the current user/Auth binding. Reset scrubs execution state, receipts and audits in the existing epoch lane; account deletion cascades the same owned data. RPC errors and lost replies do not trigger an automatic write retry. A caller retries the original operation UUID, never a newly generated ID for an uncertain request.

`training-execution-store.ts` binds owner and original Auth when constructed, validates the closed command before capture, uses the real preparation kernel and checks persisted receipts/state. A fresh reply must equal the prepared result. Replay returns the original receipt alongside current state, without a new audit. Reopening through the adapter reads the durable state rather than reconstructing prescribed sets.

The private SQL migration and adapter are source/local-qualified preparation. Staging migration reconciliation, endpoint admission/live-session authorization, native execution/recovery UI, single protected completion, user-initiated sharing and connected iOS/TestFlight qualification remain before activation. No new public capability, cloud migration or release was deployed in this increment.

Evidence: 33 kernel behavioral tests, adapter boundary tests and the full admin regression suite. `supabase/tests/training_execution_private_store.sql` checks original Auth capture/ACLs in rollback. `supabase/tests/fixtures/training_execution_store.mjs` exercises the real bundled kernel and adapter against a disposable local database: save/reopen, null versus zero, duplicate-name identity, real two-process revision race, lost reply after commit, failed-audit atomic rollback, current-state replay, changed timezone/plan, closed day, cross-account reads, reset and account-deletion cascades, and absence of workout/reward effects. Its runner requires an explicitly owned Unix-only local arena and disposable database; it accepts no hosted URL or credential. Distributed runtime, native per-exercise persistence and Roberto acceptance remain unverified.
